# 4. 計畫審查

| 檢查情境 | 計畫調整 |
| --- | --- |
| 11:30 的預約佔到 13:30，12:30 又有一組。 | 配桌比對兩筆完整區間，拒絕同一桌重疊。 |
| 仍有空位，但分散的桌子無法接待大組。 | 同時顯示空桌總座位、可接最大單組和按桌型剩餘張數，按圖上相鄰關係尋找能併桌的組合。 |
| 截止前打開表單，截止後才送出。 | 用服務端時間在寫入前重算截止及容量。 |
| 店家想掌握備餐量與到店節奏。 | 顯示整餐期合計，並依入座時間分組。 |
| 同時間收到多筆請求或重送同一事件。 | 經單行程序列化寫入，在同一交易紀錄預約和事件結果。 |
| 客人誤把定位送進群組，或拿到別人的訂位碼。 | 工作流僅限私聊，先驗證對應 LINE 使用者，再接受定位。 |
| Pages 是公開的靜態展示。 | 靜態目錄只放可公開程式、虛構資料；正式名單及密鑰留在另行部署的服務。 |

以上為同一工作階段的計畫審查。

分時兩種檢視共用相同日期、餐期與入座時間。動畫把其他時段的桌標為保留，只有當前入座時段以實心圓逐位呈現客人。

客人按了時段再填資料時，日期時間暫存在自己的對話狀態。伺服器在收到「確認」時才建立訂位，避免選了一個時段即占位或超額預約。
